## ЭТАП 2. Проверка безопасности и авторизации

### 2.1. Матрица доступа — проверь каждый пункт:

ADMIN только один, создаётся миграцией, создание других персон с ролью ADMIN в программном коде не предусмотрено. Если эта возможность есть в коде её надо удалить.

**Действия ADMIN (должны быть доступны только ADMIN):**
- POST /api/admin/users — создание пользователя
- GET /api/admin/users — просмотр всех пользователей (с фильтрацией и пагинацией и сортировкой)
- DELETE /api/admin/users/{id} — удаление пользователя
- POST /api/admin/cards — создание карты для любого пользователя (с нулевым или положительным балансом)
- GET /api/admin/cards — просмотр всех карт всех пользователей (с фильтрацией и пагинацией и сортировкой)
- PUT /api/admin/cards/{id}/activate — активация карты
- PUT /api/admin/cards/{id}/block — блокировка карты
- DELETE /api/admin/cards/{id} — удаление карты

**Действия USER (должны быть доступны только аутентифицированному владельцу):**
- GET /api/cards — просмотр только своих карт (с фильтрацией и пагинацией)
- PUT /api/cards/{id}/block-request — запрос на блокировку только своей карты
- POST /api/transfers — перевод только между своими картами

**Публичные эндпоинты (без аутентификации):**
- POST /api/auth/login
- все эндпоинты относящиеся к swagger, openapi, h2-console, healthcheck actuator

### 2.2. Потенциально опасные действия — проверь, что каждое **невозможно**:

**Горизонтальное смешение привилегий (USER атакует другого USER):**
- [ ] USER получает карты другого USER через GET /api/cards с манипуляцией параметров
- [ ] USER получает баланс чужой карты, зная её ID
- [ ] USER запрашивает блокировку чужой карты, зная её ID
- [ ] USER делает перевод с чужой карты-источника, зная её ID
- [ ] USER делает перевод на чужую карту назначения, зная её ID

**Вертикальное смешение привилегий (USER получает права ADMIN):**
- [ ] USER вызывает ADMIN-эндпоинты напрямую (должен получать 403)
- [ ] USER создаёт карту для другого пользователя
- [ ] USER создаёт карту для себя
- [ ] USER видит список всех пользователей
- [ ] USER активирует или разблокирует свою заблокированную карту напрямую (минуя запрос)

**Опасные действия ADMIN (должны быть запрещены даже для ADMIN):**
- [ ] ADMIN делает перевод между картами пользователей (у ADMIN не должно быть эндпоинта перевода)
- [ ] ADMIN видит расшифрованный номер карты в ответе API (должна быть только маска)
- [ ] ADMIN может изменить баланс карты напрямую без транзакции перевода

**Проблемы с бизнес-логикой переводов:**
- [ ] Перевод с заблокированной карты-источника
- [ ] Перевод на заблокированную карту-получатель
- [ ] Перевод с карты с истёкшим сроком
- [ ] Перевод на карту с истёкшим сроком
- [ ] Перевод с нулевой или отрицательной суммой
- [ ] Перевод суммы, превышающей баланс (уход в минус)
- [ ] Перевод с карты на ту же карту
- [ ] Race condition при одновременных переводах (отсутствие блокировки строки)

**Проблемы с данными:**
- [ ] Номер карты возвращается в открытом виде в любом ответе API
- [ ] Чувствительные данные (пароли, ключи) попадают в логи
- [ ] JWT не имеет разумного срока действия
- [ ] JWT не инвалидируется при смене пароля (если есть смена пароля)

## ЭТАП 3. Проверка схемы БД и JPA-маппинга

3.1. Соответствие миграций Liquibase и entity-классов:
- Все поля entity присутствуют в миграции с правильными типами
- Все NOT NULL в БД соответствуют @Column(nullable=false) в entity
- Все UNIQUE constraints в БД соответствуют @Column(unique=true) или @UniqueConstraint

3.2. Связи между сущностями:
- Тип связи (OneToMany / ManyToOne / ManyToMany) соответствует бизнес-логике
- FetchType.LAZY установлен везде, где коллекция не нужна немедленно
- FetchType.EAGER используется только там, где это оправдано и задокументировано
- CascadeType не установлен там, где каскадное удаление опасно (например, удаление User не должно удалять Card, если Card должна сохраняться)
- orphanRemoval используется осознанно

3.3. Проверка проблемы N+1:
- Найди все места, где в цикле вызывается репозиторий или обращение к lazy-коллекции
- Найди все JPQL/HQL-запросы — используется ли JOIN FETCH там, где нужно загрузить связанные данные
- Найди все места, где возвращается список entity со связями — нет ли неявных SELECT при сериализации в DTO
- Проверь, используется ли @EntityGraph или JOIN FETCH в репозиториях для эндпоинтов с пагинацией

3.4. Индексы:
- На полях, по которым делается поиск/фильтрация (статус карты, владелец карты, email пользователя), должны быть индексы в миграции
- Первичные ключи используют UUID или BIGSERIAL (не Int, который быстро исчерпается)

## ЭТАП 4. Проверка бизнес-логики и сервисного слоя

4.1. Транзакционность:
- Операция перевода выполняется в одной транзакции (@Transactional)
- При ошибке в середине перевода происходит rollback обеих операций (дебет + кредит)
- Нет транзакций с propagation=REQUIRES_NEW там, где это не обосновано
- @Transactional(readOnly=true) используется на всех read-only методах

4.2. Блокировка при переводе:
- При обновлении баланса карт используется pessimistic locking (@Lock(LockModeType.PESSIMISTIC_WRITE))
- Карты блокируются в детерминированном порядке (например, по ID) во избежание deadlock

4.3. Шифрование номера карты:
- Номер карты шифруется при сохранении в БД
- Маска применяется при отдаче в DTO (не в entity)
- Шифрование/дешифрование вынесено в отдельный сервис/утилиту
- В БД хранится зашифрованный номер и хэш, а не маска

4.4. Валидация входных данных:
- Все DTO с входными данными аннотированы @Valid/@Validated в контроллерах
- Все поля DTO имеют @NotNull/@NotBlank/@Size/@Min/@Max где нужно
- Сумма перевода: @Positive или @DecimalMin("0.01")
- ID пользователя/карты в path variable валидируется (не может быть отрицательным)

4.5. Статусы карт:
- Переход статуса Активна → Заблокирована корректен
- Переход статуса Заблокирована → Активна выполняется только ADMIN
- Статус "Истёк срок" проставляется автоматически по дате или проверяется при каждой операции
- Блокированная карта не может участвовать ни в каких операциях

## ЭТАП 5. Проверка обработки исключений

5.1. Наличие глобального обработчика (@RestControllerAdvice / @ControllerAdvice):
- Существует один централизованный обработчик
- Нет дублирующих try-catch в контроллерах для стандартных ошибок

5.2. Покрытие исключений:
- EntityNotFoundException / NoSuchElementException → 404 с понятным сообщением
- AccessDeniedException → 403 (не 500)
- MethodArgumentNotValidException (@Valid) → 400 со списком ошибок валидации
- Бизнес-исключения (недостаточно средств, карта заблокирована) → 400 или 422 с понятным сообщением
- DataIntegrityViolationException (дубликат username/номера карты) → 409
- Все остальные исключения → 500 без стека вызовов в теле ответа

5.3. Формат ошибок:
- Все ошибки возвращаются в единообразном формате (одна структура для всех ошибок)
- Тело ошибки содержит: статус, сообщение, timestamp (опционально: поле с ошибкой)
- Стек трейс не попадает в HTTP-ответ (только в лог)

5.4. Логирование:
- Исключения логируются на уровне ERROR с полным стеком
- Бизнес-ошибки (ожидаемые) логируются на уровне WARN или INFO, не ERROR
- Чувствительные данные не попадают в логи

## ЭТАП 6. Проверка тестов

6.1. Для каждого теста проверь:
- Тест проверяет именно то поведение, которое заявлено в названии
- Assert проверяет реальный результат, а не заглушку мока
- Мок настроен корректно и возвращает данные, соответствующие реальному сценарию
- Тест не зависит от порядка выполнения других тестов
- Нет тестов, которые всегда проходят независимо от логики (тест-пустышка)

6.2. Покрытие:
- Есть тест на успешный перевод между своими картами
- Есть тест на перевод с недостаточным балансом (ожидается исключение)
- Есть тест на перевод с заблокированной карты (ожидается исключение)
- Есть тест на попытку USER получить чужую карту (ожидается 403 или 404)
- Есть тест на попытку USER вызвать ADMIN-эндпоинт (ожидается 403)
- Есть тест на создание карты администратором
- Есть тест на блокировку карты администратором
- Есть тест на получение маскированного номера карты в ответе

6.3. Изоляция тестов:
- Unit-тесты сервисов не поднимают Spring контекст
- Интеграционные тесты используют @SpringBootTest + тестовую БД (H2 или Testcontainers)
- Нет тестов, обращающихся к реальной PostgreSQL

## ЭТАП 7. Проверка качества кода и единообразия

7.1. Архитектурное единообразие:
- Все контроллеры следуют одному стилю (нет смешения @RequestMapping на классе и методах в разных стилях)
- Все сервисы следуют интерфейс + реализация ИЛИ только реализация — единообразно
- DTO используются везде: entity не возвращаются напрямую из контроллеров
- MapStruct или ручной маппинг — единообразно, нет смешения подходов

7.2. Именование:
- Контроллеры: *Controller
- Сервисы: *Service / *ServiceImpl
- Репозитории: *Repository
- DTO: *Request/*Response или *Dto — единообразно
- Методы репозиториев следуют конвенции Spring Data (findBy*, existsBy*, deleteBy*)

7.3. Лишняя сложность:
- Нет абстрактных базовых классов, которые ничего не добавляют
- Нет паттернов (Strategy, Factory, Builder) там, где достаточно простого if/switch
- Нет вспомогательных утилитных классов, дублирующих стандартные библиотеки
- Временные README-файлы из стартовой структуры удалены

7.4. Конфигурация:
- Секреты (JWT secret, пароли БД) не захардкожены в коде — используются переменные окружения
- В docker-compose.yml используются переменные, не реальные пароли
- application.yaml не содержит production-секретов
